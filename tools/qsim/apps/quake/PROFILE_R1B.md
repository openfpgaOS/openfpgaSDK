Command (per workload, per ELF):

```sh
qsim <elf> --pak-dir <id1> --out runs/r1b/<elf>.<workload>.prof --quiet --profile --top 400 \
     --heap-size 0x2f5fb70 $(workload_opts <workload>)          # eager GPU schedule, flat memory
qsim <elf> ... --out runs/r1b/<elf>.<workload>.lazy --gpu-sched lazy --mem lint   # GPU barrier counters
analysis/pcx2/qsim_pcx <elf> ... --out runs/r1b/<elf>.<workload>.pcx --profile     # per-PC penalty classes
```

* **Heap pinned.** Both ELFs run with `caps.heap_size = 0x2f5fb70`, the baseline's device value (`0x13A00000 - bss_end`), the same value `gate.sh` pins.  Without it the candidate's larger `.bss` would shrink its Quake heap and surface cache, i.e. it would run a different workload.  Both runs report the same `35.0 megabyte heap` and `5120k surface cache`.
* **Schedule and memory.** `--gpu-sched eager --mem flat` for every profile run (the qsim default): the GPU is infinitely fast and the CPU never waits for it, so `est_cycles` is pure CPU cost.  The GPU-barrier numbers in section 8.2 come from the separate `--gpu-sched lazy --mem lint` runs.
* **Workloads** are the five in `workloads/workloads.sh`, unchanged.  Every run reached its terminator (`timedemo_complete`, or `workload_complete` for play1); no traps, no unmapped MMIO, no watchdog.
* **The per-PC penalty-class data** (sections 7.x) comes from `analysis/pcx2`, a private instrumented copy of the current qsim sources that also charges each penalty class to the pc that incurred it.  It is verified to produce byte-identical `frames.csv`, `profile.tsv`, `profile.txt`, `profile_calls.tsv` and `console.log` to stock qsim on all ten runs (`analysis/r1b/run_pcx.sh`), and its per-function class sums equal `profile.tsv` exactly (3,371 function rows across the ten runs, 0 mismatches).  No shared qsim source was modified.

**Gate status of this ELF (from `qopt/GATE_R1.md`, not re-run here).** `combined-r1b` **FAILs** the rendering-equivalence gate on 6 `fx2` frames in the three eager modes, and adds a 160-event `gpu_read_of_uncommitted_cpu_store` hazard class on `play1`.  Both trace to pre-existing baseline defects that the patch merely re-times: the conditional `pq_gpu_zwrite_pending` drain before `R_DrawParticles` (`r_main.c:1191`), and `draw_fade_pattern` sharing a 64-byte line with `r_framecount` in `draw.c`.  demo1, demo2, demo3 and play1 pass in all five modes.  Round 2 should land those two upstream fixes first; nothing in this profile depends on them.

**Reading the numbers.** `est_cycles` is a *relative* metric from a model with several GUESS parameters (section 11), not a cycle-accurate prediction, and the whole-run layout noise floor is +-0.6 % (address-only variants) to +-1.2 % (alignment variants), so a sub-0.6 % whole-run est_cycles claim is not measurable.  Per-function numbers have no confidence interval attached at all: I-cache misses move by up to 35 % and D-cache misses by up to 3 % between functionally identical layout variants.

Reading this table:

* The candidate removed **2.65 G instructions (-24.9 %)** and **3.87 G cycles (-21.1 %)** across the five workloads.  Instructions fell faster than cycles, so CPI rose from 1.722 to 1.808: what is left is more memory- and stall-bound than what was removed.
* The two classes that barely moved are **D-cache** (1.50 G -> 1.42 G, -5.0 %) and **dep:load** (990.1 M -> 934.5 M, -5.6 %).  Together they are now 16.3 % of the candidate's cycles against 13.6 % of the baseline's.  Memory is the new ceiling.
* **Control flow is the single largest penalty group**: mispredicts 1.20 G plus predicted-taken BTB redirects 1.03 G = 15.4 % of all cycles.  The BTB half is not a prediction failure - a correctly predicted taken branch costs 2 cycles on this core - so it is removed only by executing fewer taken branches (unrolling, branchless selects, larger loop bodies), not by making branches more predictable.
* The FPU dependency classes are essentially untouched (`dep:fmadd*` -1.5 %, `dep:fadd/fsub` -1.7 %, `fdiv freeze` -3.4 %): round 1 removed *soft-float*, not *float*.

Notes on the rollup:

* **Soft-float is done.**  2.76 G -> 347.6 M (-87.4 %).  What is left is almost entirely musl's `sinf`/`cosf` double kernels reached from `AngleVectors` (section 6.1).
* **Three "+%" rows are re-attributions, not regressions.**  `surfcache` +11.5 % is `D_CacheSurface` being outlined out of `D_DrawSurfaces` (`world_span` -18.6 %); together those two subsystems fell -5.9 %.  `rsetup` +27.0 % is `R_DrawBEntitiesOnList.part.0` (90.9 M in the baseline) being inlined into `R_RenderView_`; the pair is -4.8 % net.  `sprite`/`particle` are 0.07 % of the run and move on rounding.
* **Alias models did not get cheaper** (-0.0 %) even though every individual alias function did, because the patch's new `R_AliasClipRound` helper costs 104.9 M - see target T10.

### 8.2 GPU barriers and pixels waited (`--gpu-sched lazy`)

`lazy` runs the GPU as late as legally possible: it executes queued work only when the CPU observes GPU progress (a FENCE_REACHED read, a ring read-pointer read, or a kernel fence wait).  A *barrier* is such an observation with work behind it; `wait_px` is the pixels the CPU waited for.  This is a legal extreme, not a timing model - on hardware the GPU runs concurrently - but the barrier count is the number of times the CPU could be made to wait, and `px/barrier` is how much work each of those waits can hide.

Reading section 8:

* The GPU *work* is byte-identical between the two ELFs on every workload: the same span record, affine/perspective and pixel counts.  What changed is how it is delivered - the candidate writes 8,222,588 command words against 8,909,888 (-7.7 %) and calls `of_emit_finish`/fence 1,058 times against 1,368 on demo1.
* `publishes` differs between the eager and lazy tables for the same ELF because the ring is only 4096 words: with an infinitely fast GPU it never fills, with a maximally lazy one the CPU has to publish and then poll the read pointer.  The lazy figure is the worst case.
* **The candidate removed every kernel fence wait** (`barrier: kernel wait` 994-1115 -> 0 on all five workloads).  Those are the `video_wait_flip`-adjacent waits where the CPU blocked in the kernel with GPU work outstanding; the candidate has already drained by then.
* `rdptr` barriers - the CPU spinning on the ring read pointer because the ring is full - fell -42.7 % on play1 and -32.0 % on demo1 but are still 93-97 % of all barriers.  They are the only barrier class that scales with command volume, so they are the one to attack (target T13).
* `wait_px` per barrier roughly doubled on demo1 (1,406 -> 2,037) and play1 (779 -> 1,342): fewer, larger batches.  That is the right direction for a real GPU (more work in flight per sync) but it also means each remaining stall is longer.

### 10.1 The targets in full

**T6. Float-only `sinf`/`cosf` for `AngleVectors`**

* *where:* `mathlib.c + musl`
* *evidence:* 198.8 M charged to `AngleVectors` (1.38 % of all cycles; 1.40 % of demo1, 2.15 % of play1) through musl's double kernels `__sindf`/`__cosdf`
* *what to do:* musl's `sinf`/`cosf` evaluate a *double* polynomial, which on a single-precision-only FPU is soft-float: 198.8 M of the remaining 347.6 M soft-float cycles.  A float polynomial over the reduced range, or a table + interpolation, removes it.  **Bit-exactness:** the result will differ in the last ulp, which changes `viewangles`-derived floats and therefore the pixel oracle.  This is the one high-value target that cannot be gated as a no-op; it needs its own accepted-difference review.
* *estimate:* 0.90-1.30 % of the five-workload total (129.9 M-187.6 M cycles)

**T1. `R_GenerateSpans_Array` / `R_LeadingEdge_A`: drop the `aet_order[]` -> `aet_surfs[idx]` indirection**

* *where:* `r_edge.c:664`
* *evidence:* the function is 1.32 G (9.17 % of all cycles) of which 159.3 M is dep:load and 22.7 M is D-cache; its instruction count is bit-identical to the baseline's
* *what to do:* `R_LeadingEdge_A` and `R_CleanupSpan` are inlined into it (neither exists as a symbol in either ELF, and the function is 800 bytes in both).  The scanline walk reads `sort_keys[i]` sequentially but then gathers `aet_surfs[aet_order[i]][0..1]`, so every iteration is a dependent load into a random slot of the AET pool.  Storing the two surface indices next to the sort key (one 8-byte record per active edge, written when the edge is inserted) makes the whole walk sequential and removes the dependency chain.
* *estimate:* 0.60-1.10 % of the five-workload total (86.6 M-158.8 M cycles)

**T3. `_Host_Frame` / `CL_RelinkEntities`: stop walking the 180-byte entity array**

* *where:* `cl_main.c:481`
* *evidence:* 161.1 M D-cache cycles, 68 % of `_Host_Frame`'s own 235.9 M; 2,345,292 load misses
* *what to do:* `entity_t` is 180 bytes, so the `for (i=1; i<cl.num_entities; i++)` walk touches two to three cache lines per entity just to test `ent->model`.  Either keep a parallel `byte ent_has_model[]` (one line per 64 entities) or compact the live entities into an index list at parse time.  It is the densest single D-cache hotspot in the profile.
* *estimate:* 0.60-1.00 % of the five-workload total (86.6 M-144.3 M cycles)

**T2. `R_ScanEdges` + `R_StepRemoveEdges_Array`: stop re-sorting the AET every scanline**

* *where:* `r_edge.c:746, :313`
* *evidence:* 699.8 M (4.85 %), 541.8 M of it instructions, 78.1 M BTB-taken, 38.3 M mispredict; unchanged from the baseline
* *what to do:* `R_StepRemoveEdges_Array` is inlined here (no separate symbol): it steps `u` for every surviving edge and then insertion-sorts the whole array once per scanline.  Edges rarely cross, so the array is almost always already sorted: a "did anything actually swap" early-out, or merging the step and the sort into one pass, removes most of the compare traffic.
* *estimate:* 0.40-0.90 % of the five-workload total (57.7 M-129.9 M cycles)

**T7. `D_PolysetDrawSpans8`: stop writing alias pixels through the uncached alias**

* *where:* `d_polyse.c`
* *evidence:* 147.3 M uncached-IO cycles = 29 % of the function; 9,207,060 alias accesses at 16 cycles each
* *what to do:* the alias rasteriser writes each pixel and z value through the 0x5xxxxxxx uncached SDRAM alias to stay coherent with the GPU.  Writing through the cached mapping and issuing one `cbo.clean` per 64-byte line at the end of the span trades 16 cycles per pixel for ~1 cycle per pixel plus one clean per 64 - but the 16-cycle alias cost (`io_sdram_uc_extra` = 13) is a GUESS, so the size of this win is unknown until it is measured on hardware.
* *estimate:* 0.30-0.90 % of the five-workload total (43.3 M-129.9 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T4. `R_ClipEdge`: cut the per-edge float divide**

* *where:* `r_bsp.c / r_draw.c`
* *evidence:* 1.08 G (7.50 %) total, of which 212.4 M is FPU dependency stalls and 81.1 M is fdiv freeze
* *what to do:* each clipped edge does `scale = d0 / (d0 - d1)`, an fdiv that freezes the pipe for 17 cycles (GUESS) and whose result everything downstream waits for.  Two bit-exact moves: hoist the divide out of the per-vertex loop where the same denominator is reused, and issue the divide before the work that does not depend on it so the freeze overlaps.  A reciprocal approximation is **not** bit-exact and would fail the oracle.
* *estimate:* 0.30-0.60 % of the five-workload total (43.3 M-86.6 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T5. `R_RenderFace`: the surface/edge write stream**

* *where:* `r_bsp.c`
* *evidence:* 164.3 M D-cache cycles = 24 % of the function's 670.7 M; 511,350 store misses
* *what to do:* the emitted `edge_t`s and `surf_t`s are written once and read once, a scanline later, so every one of them is a cold line in both directions.  Shrinking `edge_t` (it carries fields the array AET no longer uses) or writing the emit stream through a small write-combining staging buffer would halve the traffic.
* *estimate:* 0.30-0.60 % of the five-workload total (43.3 M-86.6 M cycles)

**T8. `R_TrailingEdge_A`: replace the doubly-linked active-surface list**

* *where:* `r_edge.c:362`
* *evidence:* 446.9 M (3.10 %), of which 135.5 M is dep:load - the `surf->prev->next` / `surf->next->prev` chase
* *what to do:* 12,064,140 calls, 19 instructions each, and a third of the cost is waiting for pointer loads.  The surface list is short and bounded; an index-based intrusive list over a packed `surf_t` array (or a sorted small array) turns three dependent loads into indexed loads that the compiler can hoist.
* *estimate:* 0.30-0.60 % of the five-workload total (43.3 M-86.6 M cycles)

**T9. `of_emit_span`: shrink the per-span encode path**

* *where:* `of_gpu.h`
* *evidence:* 529.9 M (3.67 %) across 2,401,681 calls = 142 instructions per span; 66.6 M mispredict, 62.4 M dep:load, 52.0 M BTB
* *what to do:* this is already the round-1 streaming encoder, and it is still 3.7 % of the run.  22 % of its cost is branch penalty: the span kind (affine / perspective / const-z) is decided per span although it is constant for a whole surface.  Hoisting the decision to the surface level and emitting through a kind-specialised loop removes most of it.
* *estimate:* 0.30-0.60 % of the five-workload total (43.3 M-86.6 M cycles)

**T12. `D_DrawZSpans`: batch the uncached z writes**

* *where:* `d_scan.c`
* *evidence:* 74.4 M uncached-IO cycles = 55 % of the function, 4,650,977 alias accesses, identical to the baseline
* *what to do:* z spans are written 16 bits at a time through the uncached alias.  They are contiguous, so two 16-bit values can go out as one 32-bit store, halving the access count for free; the cached-plus-`cbo.clean` variant of T7 applies here too.  Same GUESS caveat.
* *estimate:* 0.20-0.50 % of the five-workload total (28.9 M-72.2 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T15. `R_DrawSurfaceBlock8_mip0`: widen the texture blit**

* *where:* `d_scan.c / d_surf.c`
* *evidence:* 604.6 M (4.19 %), 503.1 M of it instructions and 58.5 M dep:load; unchanged from the baseline
* *what to do:* the mip0 block builder reads the 8-bit texture and the light value per texel.  It is almost pure instruction cost with a load-use chain; unrolling to 4 texels and folding the two lookups into one 32-bit load per 4 texels is a standard win and is bit-exact.
* *estimate:* 0.20-0.50 % of the five-workload total (28.9 M-72.2 M cycles)

**T10. Inline `R_AliasClipRound`**

* *where:* `r_aclip.c:107`
* *evidence:* 104.9 M (0.73 %) in 2,741,052 calls of 19 instructions each; 21.9 M of it is FPU stall and freeze
* *what to do:* the round-1 patch made this `__attribute__((noinline))` while it was being validated.  It is called 6 times per clipped vertex from 12 sites; inlining it lets the compiler keep `f` in a register, drop the saturation test when the caller's range is known, and schedule the `fcvt` freeze against neighbouring work.  Bit-exact by construction.
* *estimate:* 0.20-0.40 % of the five-workload total (28.9 M-57.7 M cycles)

**T11. `D_PolysetDrawSpans8_NoZ`: undo the round-1 branch regression**

* *where:* `d_polyse.c`
* *evidence:* instructions 120.7 M -> 81.2 M (-32.7 %) but cycles 156.1 M -> 162.3 M (+4.0 %); mispredict events 1,756,865 -> 6,970,697 (+296 %), 55.8 M of penalty
* *what to do:* the rewrite traded a third of the instructions for a data-dependent branch that mispredicts 74 % of the time.  Making the same selection branchless (mask/select on the 8-bit texel) keeps the instruction win and gives back the 41.7 M of mispredict penalty.
* *estimate:* 0.20-0.35 % of the five-workload total (28.9 M-50.5 M cycles)

**T14. Delete the 500 us busy-wait in `CL_ParseServerMessage`**

* *where:* `cl_parse.c:864`
* *evidence:* 42.8 M uncached-IO cycles (0.30 % of all cycles) in 8,567,352 MMIO reads of the 0x40000004 counter, identical in both ELFs
* *what to do:* `if (cls.signon < SIGNONS) { ... while (*cyc - t < 50000) {} }` - a 500 us spin **per svc command during signon**, added as a workaround for a signon stall when several paks are loaded.  It is ~0.16 s of pure spin per level load on the device.  The right fix is to find the real ordering bug; the measurable one is to bound the wait or make it conditional on the pak count.  Note this is level-load latency, not frame time.
* *estimate:* 0.25-0.30 % of the five-workload total (36.1 M-43.3 M cycles)

**T16. `SV_RecursiveHullCheck`: play1's biggest single cost**

* *where:* `world.c`
* *evidence:* 265.1 M = **6.99 % of play1** (0 elsewhere); 31.4 M mispredict, 21.6 M D-cache, 33.3 M FPU stall
* *what to do:* round 1 already took 8 % off its mispredicts.  What is left is the recursive descent itself: 265,849 calls.  An explicit stack (no recursion), and hoisting the `planenum < 0` leaf test, is the standard transform.  Only play1 measures it - a timedemo will report zero.
* *estimate:* 0.15-0.40 % of the five-workload total (21.7 M-57.7 M cycles)

**T13. Stop the CPU spinning on the GPU ring read pointer**

* *where:* `of_gpu.h `of_gpu_kick``
* *evidence:* in the lazy schedule 58,845 of the candidate's 60,982 play1 barriers are `rdptr` spins (28,339 on demo1); the ring high-water mark is 4,095 of 4,096 words on every workload
* *what to do:* the ring is full on essentially every publish, so on hardware every `of_gpu_kick` can block.  A larger ring, or publishing at a lower watermark so the GPU always has a backlog while the CPU keeps filling, removes the stall.  **qsim cannot size this**: in the eager schedule it is 0 cycles and in the lazy schedule it is unbounded.  Device-only.
* *estimate:* 0.00-0.50 % of the five-workload total (0.0 M-72.2 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T17. `SV_CheckBottom` / `SV_CheckWaterTransition`: the monster-move float tests**

* *where:* `sv_move.c / sv_phys.c`
* *evidence:* 198.4 M + 107.5 M = 8.06 % of play1, of which 44.7 M and 23.4 M are FPU dependency stalls
* *what to do:* both are `fadd`/`fmadd` chains where each result feeds the next compare, so the 6-cycle FPU latency is exposed on every step (22 % of `SV_CheckBottom` is pure stall).  Interleaving the four corner tests of `SV_CheckBottom` so four independent chains are in flight hides almost all of it, bit-exactly.
* *estimate:* 0.15-0.35 % of the five-workload total (21.7 M-50.5 M cycles)

**T18. `memset` / `memcpy`: 213.2 M left**

* *where:* `musl`
* *evidence:* 98.8 M memset + 114.3 M memcpy; 0.0 M of the memset cost is D-cache store misses and 18.3 M of the memcpy cost is uncached-alias traffic
* *what to do:* round 1 already halved both.  The memset residue is dominated by buffer clears whose lines are never read afterwards - candidates for `cbo.zero`-style handling if the core supports it, otherwise for simply not clearing.  The memcpy residue includes 1,144,368 uncached-alias accesses (framebuffer copies) with the same GUESS caveat as T7.
* *estimate:* 0.15-0.35 % of the five-workload total (21.7 M-50.5 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T20. `flush_span_batch` / `gpu_param_span_list`: fewer, wider ring stores**

* *where:* `of_gpu.h`
* *evidence:* 28,706,038 MMIO stores costing 143.5 M (66 % and 19 % of the two functions)
* *what to do:* total MMIO stores fell from 55,903,941 to 51,109,217 in round 1; each one is 5 cycles (GUESS `io_mmio_extra` = 2 on top of `io_access_base` = 3).  If the ring accepts wider bursts, packing two command words per store halves the count.  Needs the peripheral spec.
* *estimate:* 0.10-0.40 % of the five-workload total (14.4 M-57.7 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T21. `R_RecursiveWorldNode`: the node walk's D-cache and FPU stalls**

* *where:* `r_bsp.c`
* *evidence:* 722.5 M (5.01 %), 96.0 M D-cache, 123.3 M FPU dependency stall, 65.1 M mispredict
* *what to do:* the BSP descent touches one `mnode_t` per step, and the plane dot product is a serial `fmadd` chain.  Splitting the node array into a compact "plane + children" hot array fixes both at once: fewer lines and two independent products.
* *estimate:* 0.10-0.35 % of the five-workload total (14.4 M-50.5 M cycles)

**T19. `PF_checkclient`: cache the PVS test**

* *where:* `pr_cmds.c`
* *evidence:* 101.8 M = 2.68 % of play1; 33.2 M FPU stall, 22.8 M D-cache, and 67,248 soft-float calls (`__extendsfdf2` + `__gtdf2`)
* *what to do:* it still calls `__extendsfdf2` and `__gtdf2` 33,624 times each on play1 - a `float > double` comparison that only needs a float compare; that alone is 4.2 M.  The rest is the per-call PVS walk, which Quake already rate-limits to one client per frame but recomputes from scratch.
* *estimate:* 0.10-0.30 % of the five-workload total (14.4 M-43.3 M cycles)

**T22. `R_InsertNewEdges_Array`: the per-scanline edge insert**

* *where:* `r_edge.c:236`
* *evidence:* 257.2 M (1.78 %), 6.3 M store-buffer stalls and 17.3 M D-cache
* *what to do:* the only function in the profile where the 2-slot store buffer is a visible cost (6.3 M cycles).  It writes the new edge's fields one at a time into a fresh pool slot; building the record in registers and storing it as a contiguous block lets the buffer coalesce.
* *estimate:* 0.10-0.25 % of the five-workload total (14.4 M-36.1 M cycles)

**T23. `SV_FindTouchedLeafs` / `SV_TouchLinks` / `SV_ClipToLinks`: the areanode lists**

* *where:* `world.c`
* *evidence:* 322.4 M together = 8.50 % of play1; 49.5 M D-cache and 46.2 M mispredict
* *what to do:* classic Quake link-list traversal over `edict_t`s scattered in the 35 MB heap.  A per-areanode array of `{edict index, absmin/absmax}` keeps the traversal in cache and only dereferences the edict on a hit.
* *estimate:* 0.10-0.25 % of the five-workload total (14.4 M-36.1 M cycles)

**T24. `PR_ExecuteProgram`: the QuakeC dispatch loop**

* *where:* `pr_exec.c`
* *evidence:* 171.2 M = 4.51 % of play1 in 54,677 calls; 26.6 M mispredict, 27.1 M D-cache
* *what to do:* round 1 took 11.6 % off it.  The remaining 26.6 M of mispredict is the opcode switch: an indirect jump the BTB cannot learn.  A computed-goto threaded interpreter turns one unpredictable jump per opcode into one per *opcode pair*, which is the usual 20-30 % win on this kind of core.
* *estimate:* 0.10-0.25 % of the five-workload total (14.4 M-36.1 M cycles)

**T25. `D_DrawSpans8`: the remaining span inner loop**

* *where:* `d_scan.c`
* *evidence:* 437.4 M (3.03 %), already -22.8 % better than the baseline; 71.7 M BTB-taken, 27.8 M D-cache, 10.9 M cbo
* *what to do:* the 8-pixel inner loop pays 2 cycles of BTB redirect per iteration (71.7 M total).  Unrolling to 16 halves that.  It is also the only place where `cbo` cost is visible (10.9 M), from the cache cleans that hand the span to the GPU.
* *estimate:* 0.10-0.25 % of the five-workload total (14.4 M-36.1 M cycles)

**T30. Shrink the I-cache working set of the per-frame path**

* *where:* `link order`
* *evidence:* I-cache penalty is 198.8 M (1.4 % of all cycles) spread over 466 functions; the top three are `R_RenderView_`, `R_AliasDrawModel` and `__adddf3`
* *what to do:* the I-cache is 32 KB against 511 KB of `.text`, and the per-frame path is spread across the whole image by LTO.  A profile-guided ordering that puts the ~40 functions in the frame loop next to each other is a link-time change with no semantic risk.  Note the layout noise floor: I-cache misses move +-35 % between functionally identical builds, so this must be measured over all five workloads, not one.
* *estimate:* 0.05-0.30 % of the five-workload total (7.2 M-43.3 M cycles)

**T29. Batch `mixer_set_vol_lr_h`**

* *where:* `snd_dma.c / of_smp_voice.h`
* *evidence:* 4,539 calls on demo1 and 3,712 on play1, one ecall each; app-side cost is small but the kernel side is **not modelled at all**
* *what to do:* `S_Update` sets the left/right volume of every audible channel every frame even when it did not change.  Skipping unchanged voices, or a single batched service that takes an array, removes ~4 ecalls per frame.  **qsim cannot size this**: it charges 0 cycles for the kernel side of a service call.
* *estimate:* 0.00-0.30 % of the five-workload total (0.0 M-43.3 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T26. `Turbulent8`: the water-warp span builder**

* *where:* `d_scan.c`
* *evidence:* 279.8 M (1.94 %; 3.3 % of demo2, 3.0 % of fx2), 12.8 M fdiv freeze
* *what to do:* one fdiv per 8-pixel block for the perspective correction, 12.8 M of freeze.  The same "issue the divide early" transform as T4 applies.  Water is 2.8 % of demo1 but 0.6 % of demo3, so this is level-dependent.
* *estimate:* 0.08-0.20 % of the five-workload total (11.5 M-28.9 M cycles); **size depends on a GUESS model parameter: validate on the device**

**T28. `R_RenderView_`: the per-frame D-cache cost**

* *where:* `r_main.c`
* *evidence:* 113.4 M D-cache cycles = 33 % of the function; instruction count grew +12.0 % in round 1 when `R_DrawBEntitiesOnList` was inlined into it
* *what to do:* the inline made the function 13 KB of text (11.5 KB in the baseline) that runs once per frame, which also shows up as the largest I-cache hotspot in the profile (185,584 misses).  Splitting the brush-model loop back out (`noinline`) would trade a few calls for a much smaller per-frame I-cache footprint.
* *estimate:* 0.05-0.20 % of the five-workload total (7.2 M-28.9 M cycles)

**T27. `SCR_UpdateScreen`: the last double arithmetic in the frame path**

* *where:* `screen.c`
* *evidence:* 42.6 M charged soft-float across the five workloads (19,914 direct helper calls on demo1)
* *what to do:* `SCR_UpdateScreen` still calls `__extendsfdf2`/`__muldf3`/`__divdf3`/`__truncdfsf2` ~20 times per frame - the fov/scale arithmetic and the console-height animation done in double.  Making those `float` is mechanical, but it changes rounding, so it needs the same accepted-difference review as T6 unless the values are provably exact.
* *estimate:* 0.08-0.15 % of the five-workload total (11.5 M-21.7 M cycles)

## 11. What needs the device, and why

`est_cycles` is built from the os25 timing model in `cache.c`.  Most of its parameters are read out of the VexiiRiscv generator and the Pocket RTL, but the ones below are marked GUESS in the README's parameter table because they are not derivable from those sources.  Any target whose saving is mostly made of one of these classes is sized by qsim only to within the error of that guess.

| GUESS parameter | value | what it sizes | targets it gates |
|---|---|---|---|
| `io_sdram_uc_extra` | 13 (+3 base = 16/access) | every CPU pixel and z write through the 0x5xxxxxxx uncached alias | T7, T12, T18 |
| `io_mmio_extra` | 2 (+3 base = 5/access) | every GPU command-ring store | T20, T13 |
| `fdiv_extra` | 17 cycles | the per-edge and per-span float divides | T4, T26 |
| `fsqrt_extra` | 27 cycles | vector normalisation in the server and lighting | T17 |
| `lat_fadd` / `lat_fma` | 6 / 6 | every FPU dependency chain in the profile | T4, T17, T21 |
| `lat_fmul` / `lat_fload` / `lat_i2f` | 4 / 2 / 2 | the same chains | T17, T21 |
| `dc_redo` writeback serialisation | dirty victim written back before the refill | the D-cache cost of write-heavy functions | T3, T5 |
| `sdram_wr_setup` | 8 | store-miss and writeback cost | T5, T18 |
| `bram_setup` / `bram_per_word` | 3 / 1 | APP_BRAM instruction refills | T30 |
| `io_cram_extra` | 10 | CRAM0 - unused by this build (0 accesses) | - |
| `misaligned_trap_cycles` | 400 | unused: 0 misaligned accesses in every run | - |

Beyond the parameter list, three whole effects are **not modelled at all** and can only be measured on hardware:

1. **Kernel-side cost of `OF_SVC` calls.**  qsim charges the service-table hook zero cycles and excludes its instructions.  Section 9 gives the call counts; the cost is unknown.  This is the largest single unknown in the report and it is exactly where round 1's audio cluster claims its win (the `audio_write`/`audio_get_free` drain, 72,675 calls per demo1 run in the baseline, 0 in the candidate).  T29 is in the same class.
2. **SDRAM arbiter contention.**  The GPU, the audio DMA and the scanout share the SDRAM controller with the CPU; qsim models only CPU traffic and a per-bank open row.  Every D-cache and uncached-alias number in this report is therefore a lower bound, and the targets that reduce memory traffic (T3, T5, T7, T12, T18) are worth *more* on the device than here.
3. **Real GPU throughput and concurrency.**  `eager` makes the GPU infinitely fast and `lazy` makes it infinitely late.  The truth is in between and depends on the pixel rate of `gpu_core.v`, which qsim does not model.  T13 and anything about command-ring pressure is unmeasurable here.

Finally, the FPU differences: the device FPU is generated with `--fpu-ignore-subnormal` while qsim is exact IEEE-754.  Neither ELF produced a subnormal operand or result in any run (`fpu_subnormal` is 0 everywhere), so this does not affect the comparison - but a round-2 patch that changes float ranges should re-check that counter.

## 12. Anomalies and things to be careful with

1. **Per-symbol deltas are only meaningful when the symbol survives.**  The patch outlines and inlines aggressively: `flush_span_batch.lto_priv.0` (1.16 G cycles in the baseline) is replaced by five differently named functions, `R_DrawBEntitiesOnList.part.0` is inlined into `R_RenderView_`, and `D_CacheSurface` is outlined out of `D_DrawSurfaces`.  Section 5.3 lists the symbols that exist in only one ELF; read sections 5.1 and 5.2 with it.  The same trap exists for symbols that survive: `SND_Spatialize` reads as **+2941 %** in section 5.1 only because the baseline inlined nearly all of it into `S_Update`; the pair is 114.8 M -> 76.4 M, -33.5 %.
2. **`D_PolysetDrawSpans8_NoZ` is a genuine regression** (T11): a third fewer instructions but 4 % more cycles, entirely from a new data-dependent branch.  It is the only function in the top 60 where the candidate is slower for a reason that is not a re-attribution.
3. **The `min` per-frame column is a window-edge artefact.**  Frames 31-33 of a timedemo window are the first frames after the level load; the candidate is 72 % cheaper there only because those frames draw almost nothing.
4. **fx2 is not a device configuration.**  `r_waterwarp`, `r_drawparticles`, `r_dynamic` and `d_mipscale 1.5` are all off or at default in the shipped `quake.ini`.  fx2 exists for coverage of those paths; do not weight it when ranking targets.  It is also where the candidate fails the gate (section 1) and where the baseline reports 180,943 memory-coherency hazards from the water-warp path, all of them the CPU reading a GPU-written stack buffer without invalidating.
5. **`CL_ParseServerMessage` carries 8,567,352 MMIO reads that have nothing to do with the network** - they are the 500 us signon busy-wait (T14).  Anyone reading the uncached-IO table without that context will misread it.
6. **`R_AliasClipRound` and `BoxOnPlaneSide` are new `noinline` symbols** introduced by the round-1 patches, worth 104.9 M and 7.1 M.  They are artefacts of making the patches reviewable, not design decisions; T10 covers the first.
7. **The play1 numbers are the only ones that measure the server.**  `SV_*`, `PR_*` and `PF_*` are 0.0 % of every timedemo and 38 % of play1's cycles (29 % in the baseline; the whole `host` subsystem is 43 %).  Any round-2 patch touching them must be benchmarked on play1; a demo-only benchmark would have rejected round 1's `server-model` cluster, which is worth -8.2 % there.
8. **Both ELFs execute the same GPU work.**  Span records, affine/perspective counts and pixel counts are identical on every workload (section 8.1).  That is a useful invariant to keep in round 2: a patch that changes them is changing what the GPU draws.
